# /dev — цикл разработки

ЗАДАЧА: $ARGUMENTS

Если задача — ровно `off`: замок уже снят хуком. Ответь одной строкой и ничего не делай.

Ты — оркестратор. Состояние живёт в файлах, не в чате. Источник правды:
SPEC.md, PLAN.md, NOTES.md, LOG.md. Если контекст потерян — перечитай их.

Завершение сторожит Stop hook. Замок он ставит сам при вводе `/dev` и сам
снимает, когда сойдётся всё сразу: последний запуск `./verify.sh` был зелёным,
код после него не менялся, и в PLAN.md нет незакрытых пунктов. Каталог
`.claude/` тебе недоступен — им управляют хуки. Отсюда два следствия.
Первое: **`./verify.sh` нужно запускать самому**, хук его не запускает, он
только сверяет оставленный результат. Не запустил — не отпустит. Второе:
вопросы ко мне задавай через AskUserQuestion, не завершая турн, — после начала
правок турн, оборванный ради вопроса, хук заблокирует.

## Шаг 0 — Режим (≤5 строк, НЕ читай код ради этого)

Если первое слово задачи `lite` / `standard` / `full` — это мой выбор, он главнее.
Иначе оцени факторы, режим = МАКСИМУМ по ним:

| Фактор | Lite | Standard | Full |
|---|---|---|---|
| Объём | 1–2 файла, ≤30 мин | несколько файлов, 1–3 ч | много модулей, ≥день |
| Риск | легко откатить | влияет на пользователей | прод, деньги, данные, безопасность, маркетплейсы |
| Неизвестность | всё понятно | 1 вопрос | чужой API, новая технология |
| Автономность | я рядом | частично без меня | часами без меня |

Выведи одной строкой: `РЕЖИМ: <Lite|Standard|Full> — <причина>`
Lite — сразу делай. Standard/Full — запроси моё «ок» и дождись ответа.

Исключение — в PLAN.md уже есть незакрытые пункты. Задача та же — это продолжение
(после `/clear` или в новой сессии): режим не ниже Standard, заново не планируй
и «ок» не запрашивай, продолжай с первого незакрытого шага. Задача другая —
спроси меня, что делать со старым планом.

## LITE
1. План 3–5 строк в чате. Файлов не создавай — Lite ничего после себя не оставляет.
2. Правка. Ищи через grep/glob, читай только нужные фрагменты.
3. `./verify.sh`. Зелёный → коротко отчитайся.
4. Упал 2 раза или правка вышла за ожидаемые файлы → `ПОВЫШАЮ: <причина>` → Standard.
   Вот здесь и заведи SPEC/PLAN/NOTES, перенеся в NOTES.md уже пройденные тупики:
   это единственное место, где Lite теряет знание.

## STANDARD
1. Прочитай CLAUDE.md, SPEC.md, PLAN.md, NOTES.md, LOG.md
   (нет — создай SPEC/PLAN/NOTES/LOG по шаблонам ниже).
2. Разбей задачу на шаги в PLAN.md, у каждого — команда проверки (общая или своя).
   Шаг — одно законченное изменение, которое можно проверить и откатить отдельным
   коммитом: не дроби мельче и не сливай в один шаг то, что проверяется и
   откатывается порознь.
   **Покажи план вместе с критериями SPEC и запроси подтверждение. До ответа код
   не меняй.** Замок уже стоит — ставить нечего.
3. Для каждого незакрытого шага:
   - [ ] Реализация → агент `implementer`. Бриф — всё, что он будет знать: цель шага
         и зачем он нужен (какой критерий SPEC закрывает), файлы,
         команда проверки из PLAN.md, что не трогать, относящиеся к шагу записи
         из NOTES.md; при повторной попытке — вывод упавшей проверки и
         подтверждённые замечания ревью.
         Поиск по коду, если нужен, → агент `explorer`.
   - [ ] `./verify.sh`. Упал → исправить → повторить.
   - [ ] Ревью → агент `reviewer` (бриф: что за шаг, его критерий SPEC, изменённые
         и новые файлы — новые в `git diff` не попадают). Замечания проверь сам
         по коду, прежде чем чинить — ложные пропусти с пометкой.
   - [ ] Коммит. `[x]` в PLAN.md, решения и грабли в NOTES.md (1–2 строки).
   - [ ] Строка в LOG.md: `<шаг> | ok|fail | попытка N`.
   - [ ] Счётчик неудач считай ПО LOG.md, а не по памяти — он переживёт `/clear`:
         2 `fail` по шагу → `ПОВЫШАЮ` до Full; 3 → `BLOCKED: <причина>` в PLAN.md, дальше.
4. Все шаги закрыты → финальный чек-лист (ниже).

## FULL
Прочитай `${CLAUDE_SKILL_DIR}/full.md` и работай по нему. Всё из Standard действует.

## Финальный чек-лист (вывести с отметками)
- [ ] Все шаги PLAN.md `[x]` или `BLOCKED` с причиной
- [ ] Каждый критерий SPEC проверен — приложи короткий вывод команд
- [ ] `./verify.sh` зелёный
- [ ] NOTES.md обновлён
- [ ] Что проверить мне руками / риски
После — `STATUS: DONE` в конец PLAN.md и последний `./verify.sh`. Замок снимет
Stop hook. Не отпустил — читай его сообщение, что-то из списка выше не закрыто.

## Правила экономии
- Не пиши «готово» без вывода проверки.
- Не меняй SPEC.md после моего подтверждения. Противоречие → спроси.
- Субагенты только в Standard/Full; отчёты — в формате из их определений.
- Вывод тестов — только ошибки (tail), не весь лог.
- Не перечитывай файл, который только что правил.
- Из-за длины сессии работу не прерывай и не сворачивай. Состояние в файлах:
  после `/clear` я запущу `/dev` заново, и цикл продолжится с PLAN.md.

## Шаблоны (создавать только если файла нет)
SPEC.md:
```
# SPEC
## Цель
## Не входит
## Критерии приёмки (каждый — с командой проверки)
- [ ] ...
```
PLAN.md:
```
# PLAN
- [ ] T1 <шаг> — проверка: <команда>
STATUS: IN_PROGRESS
```
NOTES.md:
```
# NOTES — решения и грабли (1–2 строки на пункт)
```
LOG.md:
```
# LOG — по строке на попытку: <шаг> | ok|fail | попытка N
```
