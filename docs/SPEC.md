# SPEC: cycle — цикл разработки для Claude Code

**Версия:** 1.1 · **Дата:** 17.09.2026 · **Автор:** Дмитрий
**Состав поставки:** репозиторий `virsis-bot/cycle`, автотесты `tests/run.sh` (90 проверок)

Что изменилось с 1.0: перестроен механизм принуждения — см. раздел 10.

---

## 1. Назначение

Набор конфигурации для Claude Code (CLI), который решает четыре проблемы автономной разработки:

1. **Потеря контекста.** На длинных задачах Claude «забывает» план и решения.
2. **Ложное «готово».** Claude заканчивает работу без реальной проверки.
3. **Нет независимой проверки.** Код проверяет тот же агент, который его писал.
4. **Лишний расход токенов.** Тяжёлый процесс запускается даже на мелких задачах.

**Подход.** Состояние хранится в файлах (SPEC/PLAN/NOTES/LOG). Процесс масштабируется под задачу (три режима). Роли разнесены по моделям разной стоимости. Критичные правила закреплены хуками, а не только текстом промпта.

## 2. Пользователь и сценарий

- **Пользователь:** один разработчик или техлид, работает с Claude Code в терминале на macOS.
- **Сценарий:** `/dev <задача>` → Claude выбирает режим → (Standard/Full) план и подтверждение → цикл «реализация → verify → ревью → коммит» → финальный чек-лист.
- **Главная модель:** выбирает пользователь (`fable`, `opus` или `opusplan`).

## 3. Входит / не входит

**Входит:** скилл `/dev` с тремя режимами; три субагента с фиксированными моделями; Stop hook, требующий пройденной проверки; PreToolUse hook с базовой защитой; UserPromptSubmit hook, включающий режим; шаблоны `CLAUDE.md` и `verify.sh`; скрипты установки и подключения; автотесты.

**Не входит:** CI/CD; автономный внешний цикл (`claude -p` в bash-цикле); логирование расхода токенов; Windows; готовые `verify.sh` под конкретные стеки; sandbox-уровень безопасности.

## 5. Функциональные требования

### 5.1 Скилл `/dev`
- **F1.** Вызывается только вручную (`disable-model-invocation: true`).
- **F2.** Принимает `[lite|standard|full] <задача>`. Явный режим главнее оценки модели.
- **F3.** Режим по максимуму из четырёх факторов: объём, риск, неизвестность, автономность. Чтение кода ради выбора режима запрещено.
- **F4.** **Lite:** план 3–5 строк в чате → правка → `./verify.sh`. Без субагентов и без файлов. *Исключение:* при повышении режима заводятся SPEC/PLAN/NOTES, и в NOTES.md переносятся уже пройденные тупики — это единственная точка, где Lite теряет знание.
- **F5.** **Standard:** SPEC/PLAN/NOTES/LOG → шаги 15–40 мин с командой проверки → **остановка до подтверждения** → по каждому шагу: implementer → verify → reviewer → проверка замечаний → коммит → обновление PLAN/NOTES/LOG.
- **F6.** **Full:** всё из Standard, плюс интервью (8–15 вопросов), разведка (≤30 мин), тесты до кода с блокировкой правок, параллельные шаги в worktree, три ревью с разным фокусом, скриншот для UI, HANDOFF.md, ретроспектива. LOG.md ведётся начиная со Standard, а не только в Full: счётчик неудач шага должен пережить `/clear`.
- **F7.** Повышение режима: 2 неудачи подряд или выход за ожидаемые файлы → уровень выше. 3 неудачи → шаг помечается `BLOCKED` с причиной. Счётчик считается по LOG.md, не по памяти модели.
- **F8.** `.claude/dev-mode` создаёт UserPromptSubmit hook при вводе `/dev`, снимает Stop hook после выполнения условий F12–F14 либо пользователь командой `/dev off`. **Модель его не создаёт и не удаляет.**
- **F9.** Финальный чек-лист выводится с отметками и выводом команд проверки; в PLAN.md ставится `STATUS: DONE`.
- **F10.** Модель обязана запускать `./verify.sh` сама. Хук проверку не запускает — он сверяет её результат.

### 5.2 Stop hook (`verify-stop.sh`)
- **F11.** Ничего не делает, если нет `.claude/dev-mode`.
- **F12.** Требует аттестацию `.claude/verify.json`, оставленную `./verify.sh`. Нет аттестации → exit 2.
- **F13.** Пересчитывает отпечаток исходников сам (`fingerprint.sh`, без участия git) и сверяет с записанным в аттестации. Не совпал — код менялся после проверки → exit 2. Совпал, но `exit != 0` → exit 2.
- **F14.** При наличии PLAN.md требует отсутствия незакрытых `- [ ]` (маркеры `-`, `*`, `+`; пункт с `BLOCKED` считается закрытым).
- **F15.** Все условия выполнены → удаляет `dev-mode`, `protect-tests`, счётчик и отпускает.
- **F16.** Счётчик блокировок сбрасывается, как только отпечаток исходников изменился с прошлой блокировки: попытка после реальной правки не наследует предыдущие. 3 блокировки подряд → четвёртая отдаёт финальное сообщение через exit 2 (stderr при exit 0 модели не показывается) и пишет `BLOCKED (hook)` в PLAN.md; пятая отпускает.
- **F17.** Работает быстрее секунды. Прогон проверок внутри хука запрещён: хук, превысивший таймаут, отменяется, и турн завершается — это fail-open.

### 5.3 PreToolUse hook (`guard.sh` + `guard.py`)
- **F18.** Разбирает команду посегментно (`;`, `&&`, `||`, `|`, перевод строки, с учётом кавычек) и дополнительно прогоняет регэкспы по всей строке как подстраховку.
- **F19.** Блокирует: `rm -r`/`-R` по цели вне проекта или по самому корню проекта; форс-пуш, включая `-f` и refspec `+branch`, с опциями `git -C`/`--no-pager`/`-c`; `git reset --hard`. `--force-with-lease` разрешён.
- **F20.** Блокирует запись в `.env`/`.env.*` через Edit/Write/MultiEdit/NotebookEdit и через shell (редирект, `sed -i`, `tee`, `cp`, `mv`). `.env.example|sample|template|dist` разрешены.
- **F21.** При `.claude/protect-tests` блокирует правки тестов теми же двумя путями. Кеши (`__pycache__`, `.pytest_cache`, `node_modules`) исключены.
- **F22.** Блокирует запись в `.claude/`, кроме белого списка `.claude/{commands,agents,skills,memory}/`, и правку `verify.sh`, пока включён режим. Сравнение путей регистронезависимо (APFS). У `cp`/`mv`/`ln` проверяются и источник, и приёмник.
- **F23.** Нет `python3` → exit 2 с объяснением. Любой сбой разбора → exit 2. Не-JSON на входе → exit 0.

### 5.3a Pre-push hook
- **F23a.** `init-project.sh` ставит `.git/hooks/pre-push`, который перед отправкой запускает `./verify.sh` **заново**, игнорируя аттестацию. Красный — push отменяется, вывод уходит вызвавшему (обычно агенту, который пушит по просьбе пользователя), так что ошибка возвращается в цикл без участия человека.
- **F23b.** Хук локальный, в репозиторий не коммитится и у коллег не появляется. Нет `verify.sh` — не мешает.
- **F23c.** `guard.sh` блокирует `git push --no-verify` и запись в `.git/` (кроме `.git/index.lock`): без этого хук снимается одной командой. У агента легитимной нужды в `--no-verify` нет, у пользователя из терминала он остаётся.

### 5.4 Установка
- **F24.** `install.sh` копирует скилл и агентов в `~/.claude`; существующие файлы → `*.bak.<timestamp>`.
- **F25.** `init-project.sh` из корня проекта. Не перезаписывает `CLAUDE.md` и `verify.sh`. Обновляет хуки, изменённые — предварительно в `*.bak.<timestamp>`. Сливает хуки в `.claude/settings.json` атомарно, сохраняя чужие ключи и не дублируя свои при повторном запуске. Дописывает служебные файлы в `.gitignore`.

## 8. Известные ограничения и риски

1. **Скилл — инструкция, а не код.** Соблюдение F3–F9 зависит от модели. Жёстко закреплены только хуки.
2. **`guard.sh` — не граница безопасности.** `eval`, `sh -c`, склейка из переменных, симлинки и фоновые процессы фильтрации по строке не поддаются. Обходится намеренно.
3. **Аттестация подделываема.** Частично компенсируется `pre-push` (F23a): он гоняет проверку заново, поэтому подделка вскрывается при отправке в remote — но до отправки турны закрываются.  Она лежит в файле, а защищает её только `guard.sh` (п. 2). Значит завершить работу с красным кодом можно одной намеренной командой. Под одним пользователем с доступным shell неподделываемой локальной аттестации не существует: ключ для подписи лежал бы там же, где её читают.
4. **Проверку можно обезвредить, не трогая защищённых файлов:** `conftest.py`, переменные окружения, подмена бинарника в PATH.
5. **`[x]` в PLAN.md можно проставить, не выполнив шаг.** Сверки с LOG.md нет.
6. **Нет `python3` → guard блокирует всё**, а `init-project.sh` падает на слиянии настроек.
7. **Отпечаток не видит** содержимое `node_modules`, `.venv`, `__pycache__` и кешей — код там считается неизменным.
8. **Крупные файлы (>256 КБ)** учитываются по размеру, `mtime`, `ctime` и inode, а не по содержимому.
9. **Блокировка тестов действует на всех агентов**, включая оркестратора. Тесты пишутся до `touch .claude/protect-tests`.
10. **Доступность моделей** зависит от тарифа и версии Claude Code.
11. **Параллельные worktree** в Full рассчитаны на поддержку `isolation: worktree`.

**Итог по модели угроз.** Кит безотказен для добросовестного агента: правильный путь дешевле обхода, состояние переживает `/clear` и потерю сессии. Против агента, целенаправленно обходящего проверку, гарантию даёт только прогон на другой машине — CI, вынесенный за скоп (раздел 3).

## 9. Ответы на вопросы версии 1.0

1. **Пороги режимов.** Численные не нужны — модель всё равно оценивает объём до чтения кода. Нужен наблюдаемый предикат: запретить Lite при незакрытых пунктах в PLAN.md.
2. **Перенести `dev-mode` в хук.** Сделано (F8). `UserPromptSubmit` срабатывает на слэш-командах и получает сырой текст промпта — проверено запуском.
3. **Усиливать `guard.sh`.** Усилен по путям записи, но границей безопасности не объявляется (п. 8.2). Прежняя неравномерность — Edit/Write закрыт, shell открыт — была хуже отсутствия запрета: агент упирался в стену и тут же находил легальный обход.
4. **Лимит блокировок.** Оставлен 3 и в конфиг не выносится: файл настройки пришлось бы защищать как замок, иначе он сам становится обходом. «Сделать счётчик на шаг» — ошибка постановки: счётчиков два и они про разное. Счётчик Stop-хука размыкает цикл завершения и к шагам отношения не имеет; лимит попыток на шаг — это F7, он считается по LOG.md и уже на шаг. Настоящий дефект был в сбросе, он устранён (F16).
5. **Метрики.** Токены на закрытый пункт PLAN.md; доля пунктов, закрытых с первого зелёного verify; доля BLOCKED. Первые две считаются из LOG.md.

## 9a. Обучение

Отдельный механизм накопления знаний не вводится: постоянный файл «уроков» грузится в каждый запрос и обесценивается по мере роста. Знание раскладывается по трём каналам — разовое в NOTES.md проекта; повторяющееся и проверяемое становится тестом в `verify.sh` (исполняемая форма, контекст не тратит, применяется без участия модели); повторяющееся и непроверяемое — не больше трёх строк в CLAUDE.md и только после второго случая. `stats.sh` даёт обратную связь человеку по LOG.md, моделью не читается.

## 10. Изменения 1.0 → 1.1

| Было | Стало | Почему |
|---|---|---|
| Stop hook пропускал, если нет изменений в рабочей копии | Сверяет отпечаток исходников с аттестацией | Коммит после каждого шага (F5) делал рабочую копию чистой, и хук не срабатывал никогда |
| Stop hook сам запускал `verify.sh` | Запускает модель, хук сверяет результат | Хук, превысивший таймаут, отменяется → «сделай тесты медленнее лимита» было обходом |
| Отпечаток из `git status` | Обход дерева без git | `git stash` и запись в `.gitignore` возвращали старый зелёный отпечаток |
| `dev-mode` создавала и удаляла модель | Ставит UserPromptSubmit, снимает Stop hook | Ключ от замка лежал в кармане у того, кого он запирал |
| Пустой `verify.sh` зелёный | Падает, пока не настроен | До настройки Stop hook штамповал любой результат как пройденный |
| `guard.sh` на цепочке grep | Посегментный разбор + регэкспы как подстраховка | Разбор по первой команде пропускал `true; rm -rf /` |
| Python внутри shell-heredoc | Отдельные `guard.py`, `fingerprint.py` | Ошибка экранирования дважды роняла хук целиком, молча |
| Тестов нет в поставке | `tests/run.sh`, 72 проверки | Критерий A1 ссылался на файл, которого в архиве не было |
